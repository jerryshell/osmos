# Osmos 重写计划

- 状态：草案
- 日期：2026-10-22
- 范围：产品方向、领域模型、架构、阶段、验证
- 不包含：实现代码、线上变更

本计划只定义目标、边界、数据形状、阶段和验证，不包含实现代码。

当前线上版本继续运行。重写在新分支完成，通过验收后切换。核心判断是：当前代码的资源模型、感知形状、控制方式和快照接口都与目标冲突，局部修补会保留错误形状，因此选择重写。

Osmos 指 Hemisphere Games 的 2009 年游戏。本计划借用其质量、动量、吞噬和喷射推进规则，不使用其美术、音乐、关卡文本或商标素材。

## 如何阅读本计划

每个阶段都给出目标、产出、验证和退出条件。验证必须同时覆盖单元、真实页面和性能三类证据。测试通过不等于完成。阶段门禁只认可复查的证据，例如命令输出、截图、录屏、性能记录和快照哈希。

参数是起点，不是承诺。Phase 0 和 Phase 2 用基线测量调整人口、质量、速度和适应度。任何数字变化都要记录原因和证据。

## 1. 结论

推荐方向是零玩家质体世界。访客不直接控制某个质体，而是选择场景、种子和速度，观察种群演化，并检查单个质体的感知和决策。

这个方向保留 shorelark 的遗传算法和神经网络，同时把 Osmos 的质量、动量、吞噬和喷射推进变成可学习的问题。手动游玩模式留到 v2，不进入 v1。

### 完成定义

v1 完成时必须同时满足以下条件。

1. 300 个实体（64 个 AI 质体，其余为颗粒、喷出物和猎手）在 1× 速度下稳定 60 fps，4× 下不低于 30 fps。500 个实体（64 个 AI 质体）在无渲染的 headless 模式达到 2,400 步/秒。
2. 一局 2,400 步。1× 约 40 秒，8× 约 5 秒。世代切换不出现白屏，主线程长任务不超过 100 ms。
3. 固定种子在同一构建内重放 1,000 步，量化快照哈希一致。
4. 30 代后，整个 64 个基因组在平静场景的 10 个留出种子上的中位最终质量不低于随机控制网络基线的 1.25 倍，且在 3 个训练种子中至少 2 个成立。
5. 手机 390×844 和桌面 1280×800 完成暂停、调速、重置、场景切换、选中质体和键盘操作，无 console 错误。
6. 静态资源 gzip 总量不超过 200 KB，wasm gzip 不超过 120 KB。

### 非目标

以下内容不属于 v1。

- 可手动操控质体的 Osmos 关卡模式。
- 联机、账号、排行榜和服务端模拟。
- 手写剧情关卡和关卡编辑器。
- 复制 Osmos 的美术、音乐、关卡文本和界面。
- 跨浏览器逐位确定性。
- WebGL 或 WebGPU 渲染。
- 原生应用。

## 2. 现状判断

### 2.1 已有基础

- Rust workspace、`wasm-bindgen`、Vite 8、SolidJS 和 Canvas 2D 已能构建和部署。
- 已有质量雏形。碰撞时较大者吸收较小者，相等质量弹开。
- 已有遗传算法。轮盘选择、均匀交叉和高斯变异可以保留思想。
- 已有神经网络。当前是 4-8-1 的 ReLU 网络。
- 已有静态部署、gzip 和缓存策略。
- 已有少量单元测试和一次浏览器验收。

### 2.2 与目标的差距

| 领域 | 当前实现 | 目标 | 影响 |
| --- | --- | --- | --- |
| 资源 | `energy: usize`，速度由能量推导 | 连续 `mass`，半径由质量推导 | 碰撞、适应度、渲染和测试都要改 |
| 感知 | 4 个象限的归一化差值 | 16 个扇区，每扇区 3 个通道 | 网络输入从 4 变为 55 |
| 控制 | 网络输出一个绝对角度，速度固定 | 网络输出二维推进向量，喷射质量产生动量 | 控制、物理和适应度都要改 |
| 演化 | 5,000 步或人口低于 50 时重置 | 固定 2,400 步一局，有适应度、留出种子和历史最佳 | 世代循环和统计要重写 |
| 世界 | 只有质体，没有食物、喷出物和猎手 | 颗粒、喷出物、猎物、猎手和场景 | 需要新的生态与生成规则 |
| 性能 | 碰撞和感知都是 O(n²)，每步分配 `Vec`，每帧 serde JSON | 空间网格、复用缓冲、扁平快照 | 当前速度上限无法支撑高倍速 |
| 确定性 | `ThreadRng`，没有种子 | 带种子的 RNG，固定遍历顺序 | 无法复现和比较世代 |
| 界面 | 单一方框，速度 1 到 100，无检查面板 | 全屏场景、HUD、检查面板、场景和种子 | 交互和信息架构要重写 |
| 测试 | 冒烟测试和实现细节断言 | 行为、守恒、确定性和真实页面 | 旧测试不能保护新行为 |

### 2.3 实测基线

当前 `osmos-cli` 在 release 模式下循环调用 `step`，每步输出一行。2026-10-22 在本机 2 核环境运行 3 次，每次 3.0 秒，输出 4,878 到 4,897 行，含 1 行启动输出，约 1,626 步/秒。

这是 CLI 吞吐，包含每步 `println!` 和格式化，不是纯仿真上限。Phase 0 的无输出基准在 300 个实体上运行 5 次，中位数 1,794.5 步/秒，范围 1,722.5 到 1,898.6。阶段计时中，300 个实体的中位数是 1,634.6 步/秒，传感器约占 84%，碰撞约占 13%；500 个实体的中位数是 784.3 步/秒，范围 769.6 到 831.4。两批运行的比例有约 3 个百分点的波动，但传感器始终第一，碰撞第二。

单核利用率约 99%，最大常驻内存约 3 MB。`perf` 被系统限制，阶段计时是当前可用的 profiler。详细方法和限制见 `docs/phase-0.md`。

3 次运行中，每次在 3 秒内结束 5 到 6 代，单代最大步数约 873 到 1,027。多数世代由人口崩溃提前结束，不是跑满 5,000 步。这个现象说明当前生态在几百步内就会失衡，重写时需要用固定局长度和质量经济来验证。

按 60 fps 计算，当前实现每帧最多约 27 步。界面上的速度 100 表示每帧 100 步，也就是 6,000 步/秒，当前实现无法持续。这个数字说明高倍速并没有真正生效，不能作为优化基线。

| 文件 | 原始大小 | gzip |
| --- | --- | --- |
| wasm | 67.76 KB | 29.42 KB |
| JavaScript | 17.84 KB | 7.35 KB |
| CSS | 2.14 KB | 0.94 KB |

### 2.4 为什么重写

当前 `Cell` 把 `energy: usize` 同时当作质量和速度来源，渲染半径直接等于能量。目标需要连续质量、半径由质量推导、动量守恒和喷射成本。把 `energy` 改成 `mass` 会改变碰撞、适应度、渲染、测试和 wasm ABI，不是局部修补。

当前 `Sensor` 是 `[f32; 4]` 四象限，网络拓扑是 `[4, 8, 1]`，输出是一个绝对角度。目标需要 16 个扇区、3 个通道、二维推进向量和 55-24-2 网络。输入、输出和物理含义同时变化。

当前 `getObjectList` 每帧用 serde 把对象列表转成 JSON。目标需要扁平数组和稳定 ID。这个接口是前端每帧的主路径，不能用兼容层保留。

当前 `Simulator` 使用 `ThreadRng`，没有种子。目标需要固定种子、固定遍历顺序和可复现快照。这个约束会影响所有随机调用点。

这些形状是基础类型和主路径，不是实现细节。局部修补会把旧形状带进新系统。这里选择重写，并在新分支上分阶段验证。

保留的部分也要明确。Rust、`wasm-bindgen`、Vite、SolidJS、Canvas 2D、静态部署、gzip 和缓存策略继续使用。遗传算法的选择、交叉和变异思想继续使用。已有测试思路保留，测试内容重写。

## 3. 产品方向

### 3.1 零玩家质体世界

质体是单个可移动、可吞噬的单位。颗粒是静止或缓慢漂移的食物。喷出物是质体喷射出的质量。猎手是脚本控制的捕食者。

访客的角色是观察者和实验者。

1. 选择一个场景和种子。
2. 观察一局。
3. 世代结束时查看种群统计。
4. 选中一个质体，查看它的感知、控制网络输出和推进方向。
5. 调整速度、场景或种子，再跑一局。
6. 比较不同世代和不同种子的结果。

零玩家不等于没有玩法。观察、比较和改变实验条件就是核心循环。手动控制会引入另一套输入、关卡和反馈，v1 不承担这部分。

### 3.2 为什么不是手动 Osmos 重制

手动重制需要玩家控制、关卡设计、碰撞反馈、胜负判定、音效和教程。它会把项目从「演化模拟」变成「游戏关卡」，并且削弱遗传算法的主线。

如果后续要做手动模式，Phase 2 和 Phase 3 的模拟核心可以复用。Phase 4 会变成玩家控制、关卡和反馈，工期与验收标准不同。本计划不按该方向展开。

### 3.3 屏幕结构

桌面端采用两栏。画布占据主区域，右侧是 280 px 检查面板。检查面板显示选中质体的质量、速度、感知条、网络输出和推进方向。

手机端采用单栏。画布全宽，底部是控制条，检查面板从底部弹出。所有可点区域至少 44 px。画布保持正方形，避免世界比例变化影响公平性。

首屏不放大段说明。画布上直接显示少量 HUD。首次访问显示一句说明和一个「开始观察」按钮。说明可以关闭，关闭状态存在本地。

### 3.4 视觉目标

- 深色流体背景，低对比网格或细微噪点，不抢质体。
- 质体按谱系着色，同一后代共享色相。
- 颗粒使用低饱和浅色。喷出物使用与母体相同的色相，透明度更低。
- 猎手使用红色外环，避免只靠填充色区分。
- 选中的质体使用白色外环，并显示推进箭头和感知扇区。
- 颜色不只承载信息。猎手、选中和危险状态同时有形状或线宽差异。

## 4. 领域模型

先定数据形状，再写逻辑。以下类型是建议形状，Phase 1 实现前可以调整字段，但不能把质量、半径和速度混成一个标量。

### 4.1 唯一资源是质量

质量是质体唯一的资源。半径由质量推导。

```text
radius = 0.012 * sqrt(mass / 1.0)
```

初始质量为 1.0，初始半径约为 0.012。颗粒质量为 0.12。猎手质量为 3.0。目标质量为 4.0。质量必须有限且大于 0。

速度是状态，不是资源。质量变化只来自吞噬、喷射、生成和反物质。封闭世界中，一步前后的总质量必须在 `1e-4` 的相对误差内相等，生成和移除除外。

不再保留独立的 `energy`。不再用整数等级表示大小。渲染半径不存储，每次由质量计算。

### 4.2 类型

| 类型 | 主要字段 | 不变量 |
| --- | --- | --- |
| `MoteId` | `u32` | 一次运行内唯一，单调递增，不复用 |
| `Mass` | `f32` | 有限且大于 0 |
| `Vec2` | `x`, `y` | 有限，位置在边界内 |
| `Mote` | `id`, `lineage`, `role`, `mass`, `position`, `velocity`, `controller`, `state`, `absorbed_pellets`, `absorbed_motes`, `ejected_mass` | 质量大于 0，终止状态不再更新 |
| `MoteRole` | `Ai`, `Hunter`, `Prey` | 角色决定控制来源和颜色 |
| `MoteState` | `Alive`, `Absorbed`, `Starved` | 只有 `Alive` 参与物理和感知 |
| `Pellet` | `id`, `mass`, `position` | 质量大于 0，静止或缓慢漂移 |
| `Ejecta` | `id`, `owner`, `mass`, `position`, `velocity`, `age` | 质量大于 0，到期转为颗粒，质量不消失 |
| `World` | `tick`, `seed`, `scenario`, `motes`, `pellets`, `ejecta`, `grid`, `stats` | 所有实体在边界内，网格每步重建 |
| `Genome` | 扁平权重和偏置 | 长度与拓扑一致 |
| `ControlNetwork` | 55-24-2 的权重和偏置 | 输入 55，输出 2，输出在 `[-1, 1]` |
| `Snapshot` | 扁平数组 | 一帧内只读，ID 稳定 |

`MoteId` 和 `Mass` 使用新类型，避免把索引、质量和普通浮点数混用。外部输入在边界解析，仿真内部不再重复校验。

数据契约在 Phase 1 前固定，避免实现时各自猜字段。

- `Mote.state` 使用 `MoteState`，取值为 `Alive`、`Absorbed` 或 `Starved`。不要用 `alive: bool`。
- 基因顺序按层、按神经元，每个神经元先 `bias` 后 `weights`。拓扑为 55-24-2，长度为 1,394。
- 快照中的 `moteRole` 取值 0 表示 AI 质体，1 表示猎手，2 表示猎物。
- 快照中的 `moteFlags` 第 0 位表示存活，第 1 位表示达到目标质量，其余位保留为 0。
- `stats` 的世代和步数是计数，质量使用世界质量单位，比例使用 0 到 1。
- 检查面板需要的 `absorbed_pellets`、`absorbed_motes` 和 `ejected_mass` 存在 `Mote` 上，不从渲染层反推。

### 4.3 状态机

一局的状态只有三种。

- `Running`：按固定步长推进。
- `GenerationEnd`：本局结束，计算适应度。
- `Evolving`：选择、交叉、变异，生成下一局。

界面的状态单独定义。

- `Loading`：加载 wasm 和场景。
- `Running`：正在推进。
- `Paused`：停止推进，保留最后一帧。
- `Evolving`：世代切换。
- `Error`：加载失败或运行时错误，显示重试。

质体的状态是终态模型。

- `Alive`：参与物理、感知和吞噬。
- `Absorbed`：被更大质体吞并。
- `Starved`：质量低于下限，剩余质量转为颗粒。

不要用多个布尔值表示暂停、运行和结束。一个枚举足够。

### 4.4 碰撞与吞噬

两个质体的半径之和大于距离时发生接触。接触后按质量比处理。

| 条件 | 结果 | 备注 |
| --- | --- | --- |
| `m1 >= 1.15 * m2` | 质体 1 吞并质体 2 | 质量相加，动量守恒，移除质体 2 |
| `m2 >= 1.15 * m1` | 质体 2 吞并质体 1 | 同上，方向相反 |
| 质量比小于 1.15 | 弹开 | 位置分离，恢复系数 0.8 |
| 颗粒接触 | 吞并 | 质量相加，移除颗粒 |
| 喷出物接触 | 吞并 | 母体在 0.3 秒内不吸收自己的喷出物 |
| 反物质接触 | 质量相减 | v1.1，不进入首个版本 |

高速质体使用固定 2 个物理子步，每个子步 1/120 秒。最大速度为 0.25 世界单位/秒，子步位移小于最小质体半径。感知和控制网络每 1/60 秒更新一次，物理和碰撞每个子步更新。不做扫掠圆检测，减少分支和浮点边界。吞噬后的速度按动量守恒计算。

```text
v = (m1 * v1 + m2 * v2) / (m1 + m2)
```

碰撞对按两个 `MoteId` 排序后处理。这样同一帧内的接触顺序固定，结果可复现。不要依赖 `HashMap` 的遍历顺序。

### 4.5 推进

控制网络输出二维推进向量，两个分量都在 `[-1, 1]`。向量长度表示喷射强度。

当长度大于 0.05 且质量高于 0.05 时，按以下步骤推进。

1. 归一化方向。
2. 计算本步喷出的质量 `dm`，上限为 `max_eject_rate * length * dt`，且不能把质量降到下限以下。
3. 在质体后方生成质量为 `dm` 的喷出物，速度为 `mote.velocity - direction * eject_speed`。
4. 对质体施加反向冲量，速度变化为 `eject_speed * dm / (mass - dm)`。
5. 从质体质量中减去 `dm`。

喷出物可以被自己或别的质体重新吸收。母体在 0.3 秒内不能吸收自己的喷出物，避免瞬间回收。喷出物到期后转为颗粒，质量不消失。质量低于 0.05 时不能推进，只能漂移或被吞并。

速度受阻力影响，阻力系数起点为 0.15/s。最大速度为 0.25 世界单位/秒。边界使用反弹，恢复系数 0.8。世界大小固定为 1.0 × 1.0。

这些数值是起点。Phase 2 用学习检查和手感评审调整。任何调整都要记录在决策日志中。

### 4.6 感知

感知采用 360 度环形，不使用前向视锥。Osmos 的威胁来自四周，前向视锥会让质体看不到身后。

16 个等角扇区，每个扇区 3 个通道。

- 质量差：该扇区内邻居的相对质量差，正数表示更大，负数表示更小。
- 接近度：该扇区内邻居的距离衰减，越近越大。
- 径向速度：邻居相对质体的径向速度，正数表示远离，负数表示接近。

邻居按距离平方衰减聚合。密集区域不会只看到最近的一个。所有通道归一化到 `[-1, 1]`。

自身状态增加 7 个输入。

- 对数质量。
- 速度。
- 到四条墙的距离。
- 剩余时间比例。

总输入为 16 × 3 + 7 = 55。感知范围为 0.25 世界单位。颗粒、喷出物、猎手和同类都进入感知。

### 4.7 控制网络

控制网络是本项目的前馈网络，负责把感知映射为推进向量。网络结构为 55-24-2。隐藏层和输出层都使用 `tanh`。输出是两个推进分量。

基因组是扁平 `f32` 数组，长度由拓扑计算。

```text
(55 + 1) * 24 + (24 + 1) * 2 = 1,394
```

不使用 ReLU。输出需要正负方向，ReLU 会把控制压到非负区间。v1 不使用循环网络。先验证前馈网络是否足够，再考虑记忆。

权重使用 Xavier 初始化。变异使用高斯扰动，每个基因的变异概率起点为 1%，标准差为 0.3。

### 4.8 适应度

一局固定 2,400 步，目标质量为 4.0。初始质量为 1.0。

```text
fitness = max(0, final_mass - 1.0)
        + 0.25 * survival_fraction
        + 0.5 * target_reached
```

死亡时最终质量记为 0，保留生存时间项。`survival_fraction` 是存活步数除以 2,400，`target_reached` 是 0 或 1。只存活不生长最多得到 0.25，觅食和吞并得到更多。达到目标质量额外得到 0.5。

每代保留 4 个精英，锦标赛规模为 3，均匀交叉，高斯变异。历史最佳基因组单独保存，不因一代表现差而丢失。

前 8 名在 10 个留出种子上复评，按中位最终质量排序，用于展示和历史最佳。学习检查使用整个 64 个基因组，不用前 8 名。随机控制网络基线使用相同场景、人口和步数。

训练时每个基因组每代只跑一局，保持 40 秒的观察循环。训练噪声由多代选择和 10 个留出种子的整体复评控制。如果 30 代曲线仍然抖动，再增加训练局数，不直接改网络结构。

### 4.9 场景

场景是参数预设，不是手写关卡。v1 只做平静和捕食两个场景。引力场景放到 v1.1。

| 场景 | 质体 | 颗粒 | 猎手 | 猎物 | 重力 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 平静 `ambient` | 64 | 140 | 0 | 0 | 无 | 学习觅食、生长和喷射成本 |
| 捕食 `sentient` | 48 | 100 | 8 | 12 | 无 | 学习躲避猎手和吞并猎物 |
| 引力 `force` | 64 | 100 | 0 | 0 | 2 个引力源 | v1.1，学习轨道和借力 |

场景配置包括人口、颗粒数量与上限、喷出物上限、颗粒质量、猎手数量、猎物数量、重力源、阻力、目标质量和局长度。配置在重置时解析一次，热路径只读。

猎手最大速度起点为 0.18，低于质体上限 0.25，给逃跑留出空间。猎手质量起点为 3.0，质体长到 3.45 以上才能反吞。

颗粒可以按固定速率补充，但有数量上限。补充速率是场景参数，用于维持食物密度，不让世界在开局后很快变成空场。

每个场景都有 `max_pellets` 和 `max_ejecta`。颗粒补充到上限。喷出物超过上限或到期时转为颗粒。颗粒达到上限时，把质量并入最近的颗粒。这样 300 和 500 的实体预算不会被无限增长的颗粒或喷出物突破，质量也不会消失。

## 5. 架构

### 5.1 Crate 边界

重写后的 Rust 代码分为 5 个 crate，Web 单独一个包。

| Crate | 职责 | 不负责 |
| --- | --- | --- |
| `osmos-core` | ID、`Vec2`、`Mass`、RNG、配置原语、`Genome`、`ControlNetwork` | 物理、渲染、UI |
| `osmos-sim` | 世界、质体、物理、感知、生成、快照 | 遗传算法、wasm、UI |
| `osmos-evo` | 选择、交叉、变异、适应度、世代驱动 | 控制网络实现、渲染、DOM |
| `osmos-wasm` | wasm ABI 和扁平数组 | 业务逻辑 |
| `osmos-headless` | 无渲染训练、基准、回放 | UI |
| `osmos-web` | SolidJS、Canvas、控件、检查面板 | 物理和演化 |

删除 `osmos-ga`、`osmos-nn` 和 `osmos-cli`。遗传算法合并进 `osmos-evo`。控制网络下沉到 `osmos-core`，由 `osmos-sim` 和 `osmos-evo` 共用。命令行工具由 `osmos-headless` 替代。

合并的理由是当前 `osmos-ga` 和 `osmos-nn` 没有独立消费者，只被模拟器使用。分开会增加 Cargo 路径、版本和边界维护，但不增加复用。控制网络放在 `osmos-core`，是因为 `osmos-sim` 每步都要计算网络输出，不能反过来依赖 `osmos-evo`。模块仍然分开，测试仍然独立。未来出现第二个消费者时再拆。

依赖方向是 `osmos-core` <- `osmos-sim` <- `osmos-evo` <- `osmos-headless`。`osmos-wasm` 依赖 `osmos-evo` 和 `osmos-sim`，只做封装。`Engine` 位于 `osmos-evo`，负责一局和世代循环。`osmos-wasm` 和 `osmos-headless` 都是薄壳。依赖不能出现环。

`osmos-wasm` 只做类型转换和内存边界，不包含规则。这样同样的逻辑可以在 headless 和浏览器中运行，测试不依赖 DOM。

### 5.2 数据流

```text
Web 控件
  -> Engine::new(seed, scenario)
  -> Engine::step(n)
  -> Engine::snapshot()
  -> Canvas 渲染
  -> GenerationStats
```

`Engine` 是唯一对外入口。

| 操作 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| `new` | 种子、场景 ID | `Engine` | 解析配置，建立世界 |
| `step` | 步数 | 无 | 固定步长推进，步数有上限 |
| `snapshot` | 无 | 扁平数组 | 一帧只读，ID 稳定 |
| `stats` | 无 | 统计对象 | 4 Hz 读取，不每帧读取 |
| `reset` | 种子、场景 ID | 无 | 重建世界，清空历史 |

场景使用枚举 ID，不在热路径传 JSON。自定义配置只在重置时解析。错误在边界返回，仿真内部信任类型。

### 5.3 固定步长

仿真步长为 1/60 秒。渲染循环使用累加器。速度是目标仿真速率，不是固定每帧步数。

- 1× 目标 60 fps，每帧最多 2 步。
- 2× 目标 60 fps，每帧最多 4 步。
- 4× 目标 60 fps，每帧最多 8 步。
- 8× 目标 30 fps，每帧最多 16 步。
- 单帧超过 16 步时丢弃多余时间，避免螺旋下坠。

8× 在 30 fps 下是 16 步/帧，合计 480 步/秒，一局 2,400 步约 5 秒。1×、2× 和 4× 仍以 60 fps 为目标。headless 目标 2,400 步/秒，留出 5 倍余量给浏览器和渲染。

渲染使用累加器余数做插值。暂停时停止推进，保留最后一帧。恢复时清空累加器，避免暂停期间积累的时间一次性补跑。

### 5.4 确定性

所有随机数来自带种子的 RNG。起点使用 `ChaCha12`，种子来自 URL 或重置参数。

固定顺序包括质体遍历、碰撞对排序、颗粒生成和变异。仿真中不使用 `HashMap` 的遍历顺序。需要查表时使用 `BTreeMap` 或排序后的 `Vec`。

确定性范围限定在同一构建。不同浏览器和不同编译器可能产生不同的浮点结果。v1 不承诺跨浏览器逐位一致。回放文件保存种子、场景和构建版本。快照哈希使用量化后的位置和质量，用于回归比较。

### 5.5 快照

快照使用扁平数组，不使用 serde，不为每个质体创建 JavaScript 对象。

| 数组 | 类型 | 内容 |
| --- | --- | --- |
| `moteIds` | `Uint32Array` | 稳定 ID |
| `moteState` | `Float32Array` | `x`, `y`, `vx`, `vy`, `mass`, `hue` |
| `moteRole` | `Uint8Array` | 0 表示 AI，1 表示猎手，2 表示猎物 |
| `moteFlags` | `Uint8Array` | 第 0 位存活，第 1 位达到目标质量 |
| `pelletState` | `Float32Array` | `x`, `y`, `mass` |
| `ejectaState` | `Float32Array` | `x`, `y`, `mass`, `ttl` |
| `stats` | 对象 | 世代和步数为计数，质量为世界单位，目标达成率为 0 到 1 |

500 个实体的快照约为 15 KB。60 fps 下约 0.9 MB/s 的复制量，可以接受。每帧复制到 JavaScript，避免持有 wasm 内存视图导致内存增长后失效。

ID 在快照之间稳定。渲染器按 ID 插值。死亡质体在下一帧消失，可以选择 100 ms 淡出，但不阻塞物理。

### 5.6 渲染

使用 Canvas 2D。500 个圆和少量线段在目标设备上足够。WebGL 和 WebGPU 不在 v1。

- `devicePixelRatio` 上限为 2。
- 画布按容器尺寸调整，保持 1:1 世界比例。
- 按 12 个谱系色相分组绘制，减少状态切换。
- 颗粒、喷出物、猎手和选中质体分别批量绘制。
- 不使用每圆 `shadowBlur`。
- HUD 每 250 ms 更新一次，不随每帧更新 Solid 信号。
- 检查面板只在选中或暂停时绘制感知扇区和推进箭头。
- `prefers-reduced-motion` 用户默认暂停，显示「播放」按钮。

### 5.7 检查面板

检查面板显示以下信息。

- 质量、半径、速度、谱系和存活时间。
- 感知条。16 个扇区，3 个通道，用三行条形图显示。
- 网络输出。两个推进分量和合成方向。
- 推进成本。本步喷出的质量、剩余质量和累计喷出质量。
- 进食记录。最近吞并的颗粒或质体数量。
- 世代统计。最佳质量、中位质量、目标达成率和存活数。

检查面板不改变仿真状态。选中只影响渲染和读取。暂停时检查面板显示最后一帧的值。

### 5.8 工具

`osmos-headless` 是主要验证工具。

```bash
osmos-headless --scenario ambient --seed 42 --generations 30 --population 64 --json
```

它输出每代的统计、步/秒、内存和最佳基因组哈希。它也可以只跑固定步数做基准。

```bash
osmos-headless --entities 500 --ai 64 --steps 2400 --json
```

浏览器验收使用 Playwright。CI 运行格式、静态检查、单元测试、构建和关键页面流程。性能基准不在每次 CI 中跑，固定机器上手动运行，记录运行次数和离散度。

## 6. 关键决策

| 决策 | 选择 | 理由 | 复查触发 |
| --- | --- | --- | --- |
| 产品形态 | 零玩家观察和实验 | 保留 shorelark 主线，避免关卡和手动控制的范围膨胀 | 学习检查失败或评审要求手动模式 |
| 资源 | 只有质量 | Osmos 的吞噬和喷射都围绕质量，双资源会制造不必要的耦合 | 质量模型无法产生有趣策略 |
| 控制 | 二维推进向量，喷射质量产生动量 | 方向自由，成本清晰，适合前馈网络 | 学习不到推进或策略退化 |
| 感知 | 360 度，16 扇区，3 通道 | Osmos 的威胁来自四周，前向视锥不合适 | 感知输入过大或学习无效 |
| 物理 | 固定 60 Hz，f32 | 简单，足够稳定，便于插值 | 出现穿透或跨构建复现需求 |
| 确定性 | 同构建种子复现 | 满足调试和回放，不承担跨浏览器成本 | 需要跨浏览器排行榜或联机 |
| 快照 | 扁平 typed arrays | 去掉每帧 JSON 和对象分配 | 数据量超出复制预算 |
| 渲染 | Canvas 2D | 500 个圆足够，代码和调试成本低 | 1,000 个以上质体或大量特效 |
| Crate 数量 | 5 个 Rust crate，其中 4 个库和 1 个 CLI | 减少边界，GA 合并进 evo，控制网络下沉 core | 出现第二个消费者 |
| Worker | v1 不使用 | 先测主线程预算，避免提前引入消息协议 | 8× 时每帧 16 步的 `step` 加 `snapshot` p95 超过 8 ms |
| 人口 | 64 个 AI 质体 | 演化多样性和浏览器性能的起点 | Phase 0 基准 |
| 场景 | v1 两个，引力后续 | 先验证学习，再扩内容 | 学习检查通过 |
| 手动模式 | 不进入 v1 | 控制、关卡和反馈是另一条产品线 | v1 稳定后 |
| 素材 | 只使用原创素材 | 避免复制 Osmos 的美术、音乐和关卡文本 | 公开发布前确认名称和商标 |

## 7. 阶段计划

| 阶段 | 结果 | 门禁 | 规模 |
| --- | --- | --- | --- |
| Phase 0 | 视觉方向、基线、工具骨架 | 两个原型和性能预算评审通过 | S，2 到 3 天 |
| Phase 1 | 可观察的世界，不含学习 | 质量守恒、确定性、300 个实体 60 fps | M，2 到 3 人周 |
| Phase 2 | 感知、控制网络、喷射推进、遗传算法 | 学习检查通过 | L，3 人周 |
| Phase 3 | 猎手、猎物、两个场景、质量经济 | 质量经济稳定，无退化策略 | M，1 到 2 人周 |
| Phase 4 | 完整界面、检查面板、手机布局 | 真实页面流程和可访问性通过 | M，2 人周 |
| Phase 5 | 性能、内存、跨浏览器、CI | 预算和 10 分钟稳定性通过 | M，1 到 2 人周 |
| Phase 6 | 预览、切换、回滚 | 线上验收和回滚演练通过 | S，1 到 2 天 |

实现约 10 到 13 人周。含演化调参约 12 到 17 人周，取决于学习检查。这个估算假设一名全职实现者，且不包含手动游玩模式和引力场景。

### Phase 0. 基线与原型

目标是把不可逆决策变成可测量证据。

- 做两个一次性视觉原型。一个偏「显微镜」，强调数据和检查。一个偏「水族箱」，强调沉浸和运动。原型只用于选择方向，不进入正式代码。
- 记录当前 headless 基线和无输出模式，至少 3 次运行，保留命令、输出和时间。用 profiler 确认热点，不把推测写成结论。
- 确定人口上限、目标设备、帧预算和是否使用 Worker。
- 建立 CI 骨架。格式、静态检查、单元测试、构建先跑起来。
- 写一页视觉目标，包含手机和桌面截图。

退出条件。

- 视觉方向确定，有截图和评审记录。
- 当前基线和目标预算写进本文件。
- 关键决策表中没有未决项，或未决项有默认值和复查时间。
- 如果评审对零玩家方向或质量模型有分歧，先运行对抗评审，不在实现中边做边改。

Phase 0 不写正式实现。原型是丢弃型 HTML 或草图，验证完即删除。Phase 0 的结果和证据见 `docs/phase-0.md`。

### Phase 1. 核心世界

目标是让世界可观察，不涉及学习。

- 建立 `osmos-core`、`osmos-sim`、`osmos-evo` 的最小路径。`Engine` 只推进世界，不含演化。再接入 `osmos-wasm` 和 `osmos-web`。
- 实现质量、半径、位置、速度、边界、颗粒、吞噬、弹开和移除。
- 实现空间网格和 2 子步碰撞，覆盖碰撞和感知查询。
- 实现固定步长、快照和 Canvas 渲染。
- 实现暂停、1×、2×、4×、8×、重置和种子。
- 加入质量守恒、无 NaN、边界和快照长度的测试。

退出条件。

- 300 个实体连续运行 60 秒，无 NaN、无越界、无 console 错误。
- 封闭世界总质量在误差内守恒。
- 同一构建同一种子重放 1,000 步，快照哈希一致。
- 手机和桌面截图通过评审。
- 1× 达到 60 fps，4× 不低于 30 fps。

Phase 1 不做控制网络、遗传算法、猎手和场景选择。Phase 1 的帧率是空载世界检查点，不是产品门禁。Phase 2 用 64 个随机网络质体重测。

### Phase 2. 感知、控制网络、喷射推进、演化

目标是让学习发生，并验证最终的推进方式。

- 实现 16 扇区 3 通道感知、自身状态和墙体距离。
- 实现 55-24-2 控制网络、基因组、交叉、变异、选择和精英保留。
- 实现二维推进、喷出物、质量成本、动量守恒和母体免疫时间。
- 实现固定 2,400 步一局、适应度、世代统计和历史最佳。
- 实现 `osmos-headless`，可以跑多代并输出 JSON。
- 实现随机控制网络基线。
- 记录 8× 下每帧 16 步的 `step` 和 `snapshot` 主线程 p95。超过 8 ms 时，在 Phase 5 加 Worker，或把 8× 降为 4×。
- 同一份源码的 native 与 wasm 跑 1,000 步，按 1e-3 量化后位置误差不超过 1 个量化单位，质量误差不超过 1%。
- 用 wasm 构建跑 10 代，最佳质量不低于第 0 代，且与 native 第 10 代的差异不超过 5%。
- 世代切换在界面上显示统计，不阻塞主线程超过 100 ms。

退出条件。

- 基因组往返、网络拓扑、感知扇区、动量守恒和适应度公式的单元测试通过。
- 同一种子重放 30 代，统计哈希一致。
- 学习检查在平静场景通过。30 代后，整个 64 个基因组在 10 个留出种子上的中位最终质量至少是随机基线的 1.25 倍，且在 3 个训练种子中至少 2 个成立。
- headless 在 500 个实体（其中 64 个 AI 质体）、2,400 步时达到 2,400 步/秒。
- 浏览器在 300 个实体（64 个 AI）下，1× 达到 60 fps，4× 不低于 30 fps。
- 8× 下每帧 16 步的 `step` 加 `snapshot` p95 不超过 8 ms，或已记录降为 4× 或加 Worker 的决定。
- native 与 wasm 的 1,000 步误差在 1e-3 量化范围内。wasm 10 代最佳质量不低于第 0 代，且与 native 差异不超过 5%。
- 浏览器世代切换无冻结。

学习检查失败时，不进入 Phase 3。先检查感知是否足够、推进成本是否过高、适应度是否奖励了错误行为。必要时减少输入或简化控制，再重跑。

### Phase 3. 猎手、猎物与场景

目标是在最终推进方式上建立 Osmos 式生态。

- 实现猎手和猎物。猎手用脚本规则追逐较小的质体，最大速度低于质体上限。
- 实现目标质量、平静场景和捕食场景。
- 调整质量经济，确保喷射有成本但不至于让质体立刻饿死。
- 加入退化策略检查。包括贴墙、原地旋转、喷空质量、只追颗粒不吞质体。

退出条件。

- 猎手追逐、猎物被吞并和反吞的测试通过。
- 捕食场景中，猎手能追逐，质体能躲避或被吞并。
- 一局结束后没有大规模质量泄漏或负质量。
- 10 个预先登记的种子中，至少 7 个出现 3 次以上吞并事件。
- 至少 5 个种子出现一次躲避：质体与最近猎手的距离先减小到 0.15 以内，然后在 60 步内增大。
- 2 名评审独立记录，分歧保留，不取平均。
- 捕食场景中，进化组在 10 个固定种子上的中位存活时间高于随机基线，且没有出现全员在 300 步内被猎手吞并。随机基线使用同一场景、同样的 10 个种子和 64 个随机基因组。

### Phase 4. 体验

目标是让新访客在 10 秒内理解画面，并能完成主要操作。

- 全屏布局，桌面检查面板，手机底部面板。
- HUD 显示世代、存活数、最佳质量和目标达成率。
- 检查面板显示感知条、网络输出、推进成本和进食记录。
- 世代统计图显示最佳质量和中位质量随世代变化。
- 场景选择、种子输入、URL 参数和重置。
- 键盘快捷键。空格暂停，方向键调速，`R` 重置，`I` 检查，`Esc` 关闭面板。
- 加载状态、错误状态和重试。
- `prefers-reduced-motion` 默认暂停。
- 首次访问说明，可关闭。
- 保留并更新 title、description、canonical 和社交分享元数据。

退出条件。

- 手机 390×844 和桌面 1280×800 完成全部主流程。
- 所有按钮和输入有可见标签，焦点可见，触控目标至少 44 px。
- 只用键盘可以完成暂停、调速、重置和选中。
- 页面无 console 错误，无横向滚动。
- 文字与背景对比度至少 4.5:1。
- 5 名未接触项目的测试者中至少 4 名能在 10 秒内说出画面在模拟什么。

### Phase 5. 加固

目标是让性能、内存和发布流程可重复。

- 调优空间网格的单元大小和查询范围。
- 按 Phase 2 的记录决定 Worker。只有每帧 16 步的 `step` 加 `snapshot` p95 超过 8 ms 时才加。
- 复用缓冲，去掉每步分配。
- 快照复制和 wasm 内存检查。
- 100、300、500 个实体的基准，其中 AI 质体为 64 个。
- 10 分钟连续运行，记录内存和帧时间。
- 跨浏览器检查。Chrome、Firefox、Safari 各一次。Safari 使用可用设备或云浏览器。
- wasm 体积和 gzip 预算。
- CI 完整化，加入 Playwright。
- 更新 README、运行说明和部署说明。

退出条件。

- 性能预算全部通过。
- 10 分钟运行内存增长低于 10%。
- wasm gzip 不超过 120 KB，静态资源 gzip 总量不超过 200 KB。
- CI 在干净环境通过。
- 线上预览使用与生产相同的压缩和缓存策略。

### Phase 6. 切换

目标是安全替换线上版本。

- 部署到预览路径或预览子域，保留当前版本。
- 在桌面和手机对比新旧版本的行为和性能。
- 准备回滚目录和一条回滚命令。
- 切换生产根目录。
- 验证 HTTPS、gzip、缓存头、wasm MIME 和 SPA fallback。
- 保留旧产物 7 天。

退出条件。

- 线上桌面和手机验收通过。
- 回滚演练通过。
- 旧产物可恢复。
- 浏览器 console 和网络请求无异常。

### 依赖和并行

Phase 0 阻塞所有实现。Phase 1 阻塞 Phase 2。Phase 2 阻塞 Phase 3。Phase 4 依赖 Phase 2 和 Phase 3。Phase 5 依赖 Phase 4。Phase 6 最后执行。

Phase 1 完成后，`osmos-sim`、`osmos-evo` 和 `osmos-web` 可以按固定接口并行。共享文件只有工作区 `Cargo.toml`、wasm ABI 和快照布局。这三处串行修改，避免多人同时改接口。

### 吞吐检查点

**阻塞第一步。** Phase 0 的视觉方向、性能预算和是否使用 Worker 必须先确定。没有这些，不开始 Phase 1。

**独立工作流。** Phase 1 后分为模拟、演化、界面三条。模拟负责世界和物理，演化负责选择、变异和世代驱动，界面负责渲染和检查。三条都依赖快照布局，所以快照布局由一个人先定。

**共享可变状态。** 仿真是单线程，世界状态不跨线程共享。每个工作流使用独立分支。合并时只接受已经通过自己门禁的分支。

**最小安全拆分。** 第一阶段由一个人完成 `osmos-core`、`osmos-sim` 和 wasm ABI。接口稳定后，再分出演化和界面。不要让多人同时改质量、碰撞和快照。

## 8. 验证

测试通过不等于完成。每个阶段必须同时有单元、真实页面和性能三类证据。

### 8.1 单元测试

| 对象 | 用例 | 断言 |
| --- | --- | --- |
| 质量 | 吞噬、喷射、颗粒 | 质量守恒，结果大于 0 |
| 半径 | 质量变化 | 半径按公式变化，不存储旧值 |
| 碰撞 | 大吞小、小撞大、近似相等 | 结果符合质量比和动量公式 |
| 穿透 | 最大速度质体穿过颗粒或另一质体 | 发生吞噬或弹开，不穿透 |
| 喷出物 | 生成、再吸收、免疫时间、到期转颗粒 | 质量守恒，母体 0.3 秒内不回收 |
| 感知 | 16 个方向、3 个通道 | 方向、距离和符号正确 |
| 基因组 | 编码、解码、长度 | 往返一致，长度匹配拓扑 |
| 网络 | 固定输入 | 输出在 `[-1, 1]`，形状正确 |
| 选择 | 锦标赛、精英 | 精英保留，适应度高者更常被选中 |

测试断言外部可观察的行为，不断言内部调用顺序。感知测试使用具体输入和期望扇区，不使用随机对象。

### 8.2 属性测试

- 任意质量、速度、位置下，一步后没有 NaN 或无穷大。
- 封闭世界总质量在 `1e-4` 相对误差内守恒。
- 质量账本由存活质体、颗粒和喷出物三部分组成。守恒测试关闭颗粒补充和反物质，前后账本差值在 `1e-4` 内。
- 任何质体的质量大于 0，位置在边界内。
- 最大速度下不穿透颗粒或另一质体。
- 喷出物到期转为颗粒，质量不消失。
- 质量低于下限的质体转为颗粒，质量不消失。
- 同一 ID 不会同时存在两个存活质体。
- 喷出物和颗粒被移除后不再参与查询。

属性测试使用固定种子和有限次数，失败时打印最小输入。

### 8.3 确定性测试

同一种子、同一场景、同一构建运行两次 1,000 步。量化位置和质量到 `1e-4`，计算 FNV-1a 哈希。两次哈希必须一致。改变种子后哈希应不同。

回放文件保存种子、场景、构建版本和哈希。跨构建不承诺一致，跨构建比较只记录事实，不作为门禁。

### 8.4 性能验证

| 指标 | 场景 | 预算 | 证据 |
| --- | --- | --- | --- |
| 帧时间 p95 | 300 个实体（64 个 AI），1×，目标手机 | 16.7 ms | 真机或云真机运行 60 秒，记录 p50、p95、p99 |
| 帧时间 p95 | 300 个实体（64 个 AI），4× | 33 ms | 同上 |
| 帧时间 p95 | 300 个实体（64 个 AI），8× | 33 ms | 同上，30 fps 目标，记录每帧 16 步的 `step` 和 `snapshot` 主线程时间 |
| 长任务 | 世代切换 | 100 ms | Performance 面板 |
| headless | 500 个实体（64 个 AI），2,400 步 | 2,400 步/秒 | 5 次运行，记录中位数和离散度 |
| 内存 | 10 分钟运行 | 增长低于 10% | 浏览器内存快照 |
| 体积 | 生产构建 | wasm gzip ≤ 120 KB | 构建输出 |
| 体积 | 生产构建 | 全部 gzip ≤ 200 KB | 构建输出 |

性能数字必须带运行次数、离散度和限制因素。不要用不同人口或不同场景的数字计算加速比。旧版和新版人口不同，只比较绝对预算。

如果只有桌面浏览器，可以用 4× CPU 降速作为代理，但必须标注为代理，不能作为最终手机验收。Playwright 负责功能流程，不负责手机帧率结论。

### 8.5 学习检查

学习检查是 Phase 2 和 Phase 3 的硬门禁。

1. 用随机控制网络跑 10 个留出种子。每个种子用 64 个随机基因组，取中位最终质量，并记录存活时间和目标达成率。
2. 用 3 个训练种子各跑 30 代，每代一局，保存每代统计和历史最佳。
3. 30 代后，取该代的 64 个基因组，在同样的 10 个留出种子上复评。每个种子跑 64 个基因组，取中位最终质量。
4. 每个训练种子与随机基线比较。3 个训练种子中至少 2 个达到 1.25 倍。
5. 记录所有种子和结果，不只报告最好的一个。

如果随机基线的中位最终质量为 0，改用 75 分位或目标达成率比较，并在结果中说明原因。不能除以 0，也不能临时换指标来让结果通过。

如果学习检查失败，先检查三件事。感知是否能看到食物和威胁。推进成本是否让质体无法移动。适应度是否奖励了原地存活。不要先加场景或加特效。

### 8.6 真实页面验证

每个阶段至少完成以下流程。

- 首次加载。显示加载状态，加载完成后开始运行。
- 暂停和恢复。暂停后画面和统计不再变化，恢复后继续。
- 调速。1×、2×、4×、8× 都有可见效果，不冻结。
- 重置。同一个种子产生相同开局。
- 场景切换。切换后人口、颗粒和猎手符合场景表。
- 选中质体。检查面板显示质量、感知和推进方向。
- 键盘。只用键盘完成暂停、调速、重置和选中。
- 减少动态。系统设置减少动态时默认暂停。
- 手机。390×844 无横向滚动，按钮可点，底部面板可关闭。
- 错误。wasm 加载失败时显示错误和重试，不白屏。

证据是截图、录屏和浏览器 console 记录。测试通过不能替代这些证据。

## 9. 风险

| 风险 | 影响 | 缓解 | 触发信号 |
| --- | --- | --- | --- |
| 演化不学习 | 高 | 先做随机基线，限制输入和输出，Phase 2 硬门禁 | 30 代后仍不优于随机 |
| 退化策略 | 高 | 质量成本、猎手、目标质量、退化策略检查 | 贴墙、原地旋转、喷空质量 |
| 性能不足 | 中 | 空间网格、扁平快照、帧预算、Worker 备选 | 4× 低于 30 fps 或长任务超过 100 ms |
| 画面过密 | 中 | 谱系色、批量绘制、检查时才显示感知 | 500 质体时看不清或帧率下降 |
| 范围膨胀 | 高 | 明确的非目标，v1 只做两个场景 | 出现手动模式、关卡编辑器或联机需求 |
| 跨浏览器差异 | 低 | 同构建确定性，跨构建只记录 | 回放哈希不一致 |
| wasm 体积 | 低 | 去掉 nalgebra 和 serde 热路径，体积预算 | gzip 超过 120 KB |
| 名称和素材 | 中 | 只用原创素材，公开发布前确认名称使用 | 使用 Osmos 美术、音乐或关卡文本 |
| 切换故障 | 低 | 预览、回滚目录、7 天保留 | 线上 404、MIME 错误或缓存旧入口 |

## 10. 开放决策

以下决策已有默认值。没有评审反对时，按默认值推进。

| 决策 | 默认值 | 理由 | 复查时间 |
| --- | --- | --- | --- |
| 是否做手动游玩 | v1 不做 | 保持演化为核心，避免关卡和输入范围膨胀 | v1 学习检查通过后 |
| 是否使用定点数 | 不使用 | f32 足够，定点会增加实现和调参成本 | 需要跨浏览器回放时 |
| 是否使用 Worker | 不使用 | 先测主线程预算，避免提前引入消息协议 | 8× 主线程每帧 16 步的 `step` 加 `snapshot` p95 超过 8 ms |
| 人口上限 | 64 个 AI | 演化多样性和手机性能的起点 | Phase 0 基准 |
| 场景数量 | 平静和捕食 | 先验证学习，再扩引力 | Phase 3 结束 |
| 公开名称 | 暂用 Osmos 作为内部代号 | 避免在产品和品牌未定时改仓库名 | 公开发布前 |
| 持久化 | URL 种子，无账号 | 静态站点足够，不做服务端 | 需要分享基因组时 |
| 引力场景 | v1.1 | 先验证质量、推进和捕食 | Phase 4 后 |

## 附录 B. 被否决的方案

| 方案 | 为什么考虑 | 为什么不选 |
| --- | --- | --- |
| 局部重构当前代码 | 改动小，保留部署 | 质量、感知、控制、ABI 和 RNG 都是基础形状，修补会保留错误结构 |
| 手动 Osmos 重制 | 更接近原作 | 需要玩家控制、关卡、胜负和教程，削弱演化主线，v1 范围过大 |
| ECS 或 Bevy | 数据导向，扩展方便 | 500 个质体不需要完整 ECS，依赖和阅读成本高于收益 |
| WebGL 渲染 | 更多粒子和特效 | 500 个圆用 Canvas 2D 足够，先解决模拟和体验 |
| 定点数物理 | 跨浏览器确定性 | 实现和调参成本高，v1 只需要同构建复现 |
| NEAT 或拓扑演化 | 自动发现网络结构 | 难以检查和复现，GA 固定拓扑已足够验证核心问题 |
| 服务端模拟 | 防作弊和联机 | 静态站点是当前产品形态，没有账号和联机需求 |
| 先上 Worker | 界面更流畅 | 先测主线程预算，避免提前引入消息协议和状态同步 |
| 保留 GA 和 NN 两个 crate | 边界清晰 | 没有独立消费者，合并减少 Cargo 和版本边界 |
| JSON 快照 | 实现简单 | 每帧序列化和对象分配是主路径成本，扁平数组更合适 |
| 保留 `energy` 兼容层 | 迁移平滑 | 新旧资源模型并存会让碰撞、适应度和渲染长期分叉 |
